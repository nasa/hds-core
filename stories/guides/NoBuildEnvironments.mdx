# No-Build Environments

HDS Core works without a build step. If your site is static HTML, a CMS theme, or a legacy framework, you can adopt NASA's typography, color, links, and components by copying three directories onto your server and referencing three files from your pages. Node.js is optional and only used to fetch the package.

Before using this guide, confirm your site is approved to remain standalone. See [Getting Started](?path=/docs/overview-getting-started--docs) if you haven't already.

## Copy the files onto your server

Download `hds-core-v<version>-dist.zip` from the [latest release](https://github.com/nasa/hds-core/releases) and unpack it. Put the three directories it contains somewhere your web server serves, keeping them together:

{/* prettier-ignore */}
```
your-site/
├── hds/
│   ├── css/       hds.min.css, plus the two optional bundles
│   ├── js/        uswds.min.js and uswds-init.min.js
│   └── assets/    fonts/ and img/, including both SVG sprites
├── css/           your own stylesheets
├── img/
└── index.html
```

With npm available, `npm install --save-exact @nasa-hds/core @uswds/uswds` puts the same three directories in `node_modules/@nasa-hds/core/dist/`. Copy them out to your web root, since `node_modules` is not something to serve. Pinning the exact version is worth doing before v1.0, while minor releases can still rename custom properties and change component styling.

### Verify the download

npm checks package integrity for you. Downloading the zip from the [Releases page](https://github.com/nasa/hds-core/releases) puts that check in your hands. Every release publishes the SHA-256 of its dist zip twice: in the release notes, and as a `hds-core-vX.Y.Z-dist.zip.sha256` asset beside the zip.

Download both, then confirm the hash before extracting:

```sh
sha256sum -c hds-core-vX.Y.Z-dist.zip.sha256
# hds-core-vX.Y.Z-dist.zip: OK
```

On macOS, where `sha256sum` is absent, compare the digest against the release notes by hand:

```sh
shasum -a 256 hds-core-vX.Y.Z-dist.zip
```

A mismatch means the file was corrupted or tampered with in transit, so do not deploy it. Re-download, and if it still fails, [open an issue](https://github.com/nasa/hds-core/issues).

<Note type="code">**Copy whole directories.** `hds.min.css` resolves webfonts and icons as `../assets/…`, so `css/` and `assets/` have to stay siblings. Inter is also split by Unicode range, so copying only the font files the CSS visibly references drops the extra range files and leaves Polish, Russian, and Vietnamese pages in a system font. That failure is invisible if you test in English. To serve assets from an unrelated location, see [Sass Configuration](?path=/docs/guides-sass-configuration--docs).</Note>

## Reference the three files

| File                   | Where it goes                   | What it does                                                                        |
| ---------------------- | ------------------------------- | ----------------------------------------------------------------------------------- |
| `js/uswds-init.min.js` | `<head>`, before the stylesheet | Marks the page as still loading, so nav, banner, and modal content don't flash open |
| `css/hds.min.css`      | `<head>`                        | Everything visual: all USWDS components, HDS theming, typography, and the grid      |
| `js/uswds.min.js`      | End of `<body>`, deferred       | Component behavior for accordions, modals, and navigation                           |

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Your page title</title>

    <script src="/hds/js/uswds-init.min.js"></script>
    <link rel="stylesheet" href="/hds/css/hds.min.css" />
  </head>

  <body class="hds-global-styles hds-palette-white">
    <!-- your existing content, unchanged -->

    <script src="/hds/js/uswds.min.js" defer></script>
  </body>
</html>
```

`hds.min.css` is self-contained. It includes all USWDS components, HDS overrides, and every foundation style including the grid, so no other CSS file is required.

If your pages predate responsive design, the `viewport` meta tag above is step zero. Without it a phone renders the page at desktop width and scales it down, so no amount of grid work will produce a usable mobile layout, and "functional and readable on mobile devices" is one of the [design standards](?path=/docs/overview-design-standards--docs).

## Turn on HDS styling

The two classes on `<body>` are what carry HDS into your existing markup.

| Class               | What it does                                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `hds-global-styles` | Styles plain HTML in that subtree: headings, paragraphs, links, lists, tables, blockquotes, code, figures              |
| `hds-palette-white` | Sets text and link colors from the White palette. Without a palette class, body text stays the browser's default black |

Put them on `<body>` for a whole page, or on a wrapper for one region. Add `hds-global-styles-reset` to any subtree HDS should leave alone, such as a third-party widget, an embedded map, or a legacy component you are not ready to touch.

```html
<body class="hds-global-styles hds-palette-white">
  <h1>Goddard Instrument Data Archive</h1>
  <p>Body copy, links, and lists pick up HDS styling with no classes of their own.</p>

  <div class="hds-global-styles-reset">
    <!-- untouched: renders exactly as it did before HDS -->
  </div>
</body>
```

<Note type="code">
  **Without these classes, loading the stylesheet changes nothing you can see.** HDS waits to be asked rather than restyling every element on a page it does not own, so bare `<h1>`, `<p>`, and `<a>` render as they did before. The alternative to the two classes above is adding USWDS classes element by element: `.usa-prose` on a content block, `.usa-link` on links, `.usa-button` on buttons. [Typography](?path=/docs/foundations-typography--docs) compares the two approaches.
</Note>

## Self-hosting: there is no CDN

HDS Core is distributed as files you host yourself. There is no NASA-hosted CDN, and third-party mirrors such as jsDelivr and unpkg are not supported, since a `.gov` page should not depend on a third-party origin for its styling. Serve the files from your own domain as described above.

## Use HDS tokens in your existing CSS

Once `hds.min.css` is loaded, HDS design tokens are available as CSS custom properties anywhere in your stylesheets. The [Design Tokens](?path=/docs/overview-design-tokens--docs) page lists all of them, searchable, covering color, spacing, layout, typography, borders, and focus.

### Typography

```css
body {
  font-family: var(--hds-font-family-body); /* Public Sans */
}

h1,
h2,
h3 {
  font-family: var(--hds-font-family-heading); /* Inter */
}

code,
pre {
  font-family: var(--hds-font-family-code); /* DM Mono */
}
```

### Colors

Replace hardcoded values with HDS tokens. Common mappings:

```css
/* Before */
.my-heading {
  color: #0b3d91;
}
.my-text {
  color: #17171b;
}
.my-error {
  color: #e52207;
}

/* After */
.my-heading {
  color: var(--hds-color-nasa-blue);
}
.my-text {
  color: var(--hds-color-carbon-90);
}
.my-error {
  color: var(--hds-color-nasa-red);
}
```

### Overriding HDS styles

HDS Core reserves a `site` cascade layer for your overrides. Wrapping your styles in this layer guarantees they win over HDS defaults without `!important`:

```css
@layer site {
  .my-component {
    border-radius: 0;
  }
}
```

Any CSS you write outside a named layer also wins over `@layer site` by default, so most existing stylesheets will already take precedence over HDS without any changes.

## Modernize your markup incrementally

You do not need to rewrite your application all at once. The areas below are the most common sources of compliance failures. Work through them in order of impact.

### Layout: move off fixed widths

Fixed-width containers break on mobile and fail responsive layout requirements. Replace them with USWDS grid classes as an intermediary step:

| Legacy pattern                | HDS equivalent              | Notes                       |
| ----------------------------- | --------------------------- | --------------------------- |
| `width: 960px` on a container | `grid-container`            | Max-width centered layout   |
| `container-fluid`             | `grid-container-desktop-lg` | Full-width variant          |
| `row` (Bootstrap)             | `grid-row`                  | Wraps columns               |
| `col-md-3` (Bootstrap)        | `tablet:grid-col-3`         | Breakpoint as prefix        |
| `float: left` layout          | `grid-col` + `grid-row`     | Replace float-based columns |

```html
<!-- Before: broken on mobile -->
<div style="width: 960px; float: left;">
  <div class="col-md-3">Sidebar</div>
</div>

<!-- After: responsive -->
<div class="grid-container">
  <div class="grid-row">
    <div class="grid-col-12 tablet:grid-col-3">Sidebar</div>
  </div>
</div>
```

> The grid ships inside `hds.min.css`, so there is nothing extra to load. Utility classes are the exception: `.padding-2`, `.margin-top-3`, and `.text-primary` live in the optional `hds-uswds.min.css` bundle. Grid classes are a useful migration step, and the longer-term goal is native CSS Grid and Flexbox.

### Semantics: fix inaccessible markup

Visual compliance requires semantic HTML. Screen readers and keyboard users cannot interact with non-semantic elements regardless of how they are styled.

Common patterns to fix:

- **Fake buttons:** Replace `<div onclick="...">` and `<a>` tags used as buttons with `<button type="button">`.
- **Fake links:** Replace `<span onclick="...">` with `<a href="...">`.
- **Table layouts:** Replace `<table>` used for positioning with `.grid-container` and `.grid-col` classes. Tables are for tabular data only.
- **Unlabeled inputs:** Ensure every `<input>`, `<select>`, and `<textarea>` has a `<label>` linked via matching `for` and `id` attributes.

After fixing your markup, press `Tab` to navigate your site. Every interactive element must show a visible focus ring. If an element is skipped or shows nothing, the underlying HTML needs attention.

### USWDS component markup

For components that require specific HTML structure (accordion, modal, navigation), use the markup from the [USWDS component documentation](https://designsystem.digital.gov/components/overview/). HDS Core styles these components automatically when the correct markup is present, and `uswds.min.js` supplies their behavior, so there is no need to install USWDS separately.

### Icons

Both sprites ship in the `assets/img/` directory you copied. Point `<use href>` at your own path:

```html
<!-- HDS icons -->
<svg class="hds-glyph" aria-hidden="true" focusable="false">
  <use href="/hds/assets/img/hds-sprite.svg#download"></use>
</svg>

<!-- USWDS and Material icons -->
<svg class="usa-icon" aria-hidden="true" focusable="false">
  <use href="/hds/assets/img/sprite.svg#search"></use>
</svg>
```

Both classes size themselves to the surrounding text (`1em`) and take its color. A third class, `.hds-icon`, appears in component markup and is sized by the component around it, so it needs a container such as `.hds-btn-icon`. See [Icons](?path=/docs/foundations-icons--docs) for the full inventory.

## What HDS Core does not style yet

The [design standards](?path=/docs/overview-design-standards--docs) require an agency header carrying the federal government banner, the NASA logo linking to nasa.gov, and the Explore navigation, plus an agency footer with required links, the Responsible NASA Official, a contact, and a "Last Updated" date. **HDS Core does not style these yet.** Dedicated HDS versions arrive with the navigation work planned for the first post-v1.0 release. See the [Roadmap](?path=/docs/overview-roadmap--docs).

Until then, build them from the [USWDS banner](https://designsystem.digital.gov/components/banner/), [header](https://designsystem.digital.gov/components/header/), [footer](https://designsystem.digital.gov/components/footer/), and [identifier](https://designsystem.digital.gov/components/identifier/) markup. They render as stock USWDS with HDS typography and color applied, and they are readable in every palette. Expect their appearance to change when the HDS versions land, and keep any local adjustments in `@layer site` so they are easy to find and remove later.

## Updating to a new version

1. Read the [release notes](https://github.com/nasa/hds-core/releases) first. Pre-v1.0 minor releases can rename or remove CSS custom properties and change component styling, and a renamed `--hds-*` property fails silently in your own CSS.
2. Replace `css/`, `js/`, and `assets/` wholesale rather than merging them file by file. Releases add and remove font and icon files, and a partial update leaves you with a mix.
3. Confirm what you are running. Every bundle opens with a banner comment naming its version, and `hds.min.css` reports it at runtime:

   ```js
   getComputedStyle(document.documentElement).getPropertyValue('--hds-version').trim(); // 0.9.0
   getComputedStyle(document.documentElement).getPropertyValue('--hds-uswds-version').trim(); // 3.13.0
   ```

4. Re-check your pages at mobile and desktop widths, and tab through them once.

## What requires a build step

Some HDS features need a Sass compiler:

- Serving `assets/` from a location that is not a sibling of your CSS
- Customizing USWDS theme settings (colors, fonts, spacing scale)
- Using `$hds-color-*` Sass variables in your own component styles
- Using USWDS design token functions (`family()`, `size()`, `units()`)

See [Installation](?path=/docs/overview-installation--docs) for Sass setup instructions.
